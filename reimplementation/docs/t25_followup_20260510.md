# T=25 PushT/Wall Follow-up Report

Date: 2026-05-10

## Executive Summary

This round made the T=25 PushT/Wall reproduction path substantially more reliable, but it also clarified an important boundary:

- Wall is now in good shape: oracle-video GVP-WM reaches `0.98` on 50 episodes, and WAN-0S GVP-WM reaches `0.90` on the selected 10-episode batch.
- PushT WAN-0S is also in good shape for the Table-2 scale: the selected WAN-0S batch reaches `5/9 = 0.556`, matching the paper target `0.56`.
- PushT oracle remains the hard case. A robust direct-action diagnostic reaches `46/50 = 0.920`, but the paper-style smooth `tanh` action parameterization is lower (`0.70` to `0.85` depending on history handling). Therefore we should not claim exact Table 2 reproduction for PushT oracle yet.

The current state is not a hack: no success thresholds were changed, no expert actions were used in WAN-0S/GVP-WM evaluation, and the environment/action/frame-skip path was validated by direct expert replay. The main remaining gap is numerical optimization robustness in PushT contact-heavy segments.

## What Was Fixed

Paper-faithful or setup-level fixes:

- DINO-WM inference is now deterministic and frozen during planning: `eval()` plus `requires_grad_(False)`.
- Raw horizon `T=25` is consistently mapped through `frame_skip=5` to a 5-step world-model horizon.
- Planner supports DINO history ablations without forcing repeat-padded initial history; PushT WAN-0S uses no-pad initial history by default because it matched the online rollout semantics better.
- PushT and Wall oracle scripts expose learning rate, history action padding, no-pad initial history, refinement objective, refinement variance, and world-model history length as CLI parameters.
- PushT oracle can optionally build oracle guidance by replaying the expert segment in the live env (`--target-source env-replay`) to diagnose dataset/video drift.
- PushT oracle writes compact JSON summaries through `--output-json`, which made Slurm diagnostics reproducible.
- Snellius scripts now avoid bytecode/XDG cache quota problems while keeping `TORCH_HOME=$HOME/.cache/torch`, so DINOv2 uses the known cached snapshot instead of downloading upstream `main`.

Diagnostics that were tried and rejected:

- Setting PushT goal pose or relying on env-replay target did not explain the main failures.
- World-model train mode was worse and was removed.
- `wm_history_length=1` was not a fix.
- Refinement objective `"planner"` was worse than the paper-style terminal goal ranking.
- Raw-parameter MPC warm-start was rejected because it conflicts with post-solver local refinement and performed badly.

## PushT Oracle Failure Analysis

The 50-sample direct-action run failed four specs:

- `6:9`, near miss: `block_diff=20.18`, angle OK.
- `1:45`, block-position failure.
- `4:27`, block-position and orientation failure.
- `4:45`, block-position failure.

Follow-up diagnostics:

- Direct expert replay succeeds on all four specs with small errors, so env reset, action scaling, frame skip, and target states are correct.
- No-pad direct-action fixes `6:9` but not the other three.
- Refinement with 2000 samples fixes `6:9` and `4:45`, but not `1:45` or `4:27`.
- Env-replay target fixes `4:45`, but not `6:9`, `1:45`, or `4:27`.
- Expert-action warm-start fixes `6:9`, `1:45`, and `4:45`, but `4:27` still fails on orientation.
- Expert-action warm-start plus action prior still fails `4:27`, suggesting ALM/video/goal terms can pull this contact segment away from the expert trajectory.

Interpretation: remaining PushT oracle failures are planner optimization failures on contact-heavy local minima, not setup bugs.

## Is This Cheating?

No, for the reported robust sanity numbers:

- Success criteria were not changed.
- Expert actions were not used in the direct-action oracle run.
- WAN-0S evaluation did not use expert actions or oracle states.
- World models and Wan2.1 were not fine-tuned.
- Direct expert replay and expert warm-start are explicitly diagnostic only.

However, the direct-action oracle result is not exactly the paper implementation because the paper reports using a smooth `tanh` action parameterization. Direct-action clamp is a numerical robustness diagnostic. It is acceptable to report as "our robust oracle sanity reaches 0.92", but not as "we exactly reproduced paper PushT Oracle 0.98".

## Recommended Reporting Language

Safe statement:

> We fixed the setup-level issues and now have strong T=25 sanity results. Wall oracle reaches 0.98 and Wall WAN-0S reaches 0.90 on the current selected batch. PushT WAN-0S reaches 0.556, matching the paper's 0.56 scale. PushT oracle is still the remaining gap: a robust direct-action variant reaches 0.92 over 50 sampled targets, but the paper-style tanh parameterization remains lower, so we should not claim exact PushT Oracle Table 2 reproduction yet.

Avoid saying:

> We fully reproduced Table 2.

That is not yet true because PushT oracle is below `0.98` under the paper-style action parameterization and the WAN-0S batches are selected/local rather than the exact paper 50-pair set.

## Next Steps

The most useful next technical work is not more WAN generation. It is PushT oracle optimization:

- Revisit the ALM objective balance for contact-heavy orientation changes, especially where video/goal terms pull away from expert-feasible actions.
- Add a principled action-prior or trust-region variant initialized from previous MPC solves, not expert actions.
- Compare final action sequences against expert replay for the persistent `4:27` case.
- If the paper authors' implementation is available, audit their exact smooth action parameterization and refinement order.
